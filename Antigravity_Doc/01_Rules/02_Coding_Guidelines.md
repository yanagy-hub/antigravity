# コーディング規約

本プロジェクトにおけるコーディング規約およびバージョン管理のルールを定義します。

## 1. 全般的な設計原則

*   **DRY (Don't Repeat Yourself)**: コードの重複を避け、再利用可能なコンポーネントを作成します。
*   **KISS (Keep It Simple, Stupid)**: 必要以上に複雑な設計や過剰な抽象化を避け、シンプルなコードを維持します。
*   **SOLID原則**: オブジェクト指向設計の基本原則に従い、保守性の高いコードを目指します。

## 2. 命名規則

*   **明確さ優先**: 変数名や関数名は、省略を避け、役割や意図が明確に伝わる名前を付けます。（例: `usr` ではなく `user`, `calc` ではなく `calculateTotal`）
*   **統一性**: プロジェクト内で使用する用語（例: ユーザー、アカウント等）は統一します。
*   （※言語別の詳細な命名規則（キャメルケース、スネークケース等）は、採用する言語の標準的なベストプラクティスに従うものとします。）

## 3. コメントとドキュメンテーション

*   **言語**: コード内のコメントおよび Docstring は原則として **日本語** で記述します。
*   **Why を書く**: 「何をしているか(What)」はコードを読めばわかるように書き、コメントには「なぜその実装にしたか(Why)」や「制約事項」を記述します。
*   **関数のドキュメント**: 複雑な関数や公開APIには、引数・戻り値・目的を記述したドキュメント（Docstring, JSDoc等）を付与します。

## 4. バージョン管理 (Git) コミット規約

コミットメッセージは、変更の意図が後から見てもわかりやすいように、プレフィックスを付けて記述します。

### コミットメッセージフォーマット

```text
<タイプ>: <短い説明（日本語可）>

<詳細な説明（必要に応じて）>
```

### タイプの種類
*   `feat:` 新機能の追加
*   `fix:` バグ修正
*   `docs:` ドキュメントのみの変更
*   `style:` コードの意味に影響を与えない変更（空白、フォーマット、セミコロン欠落など）
*   `refactor:` バグ修正や機能追加ではないコードの書き換え
*   `perf:` パフォーマンスを向上させるコードの変更
*   `test:` テストの追加や既存テストの修正
*   `chore:` ビルドプロセスや補助ツールの変更
